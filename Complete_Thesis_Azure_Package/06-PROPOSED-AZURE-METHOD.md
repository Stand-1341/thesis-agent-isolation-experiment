# Proposed Azure method revision — draft, not collected results

This is a working replacement for the original cross-provider method. It must be reviewed against the complete thesis and finalized before collecting measured observations. The original thesis remains unchanged. Non-counted Azure pilots have been performed; no measured Azure study trial has been performed.

The proposed comparison uses an Ubuntu Linux virtual machine, Azure Functions Flex Consumption, and an Azure Container Apps custom container session pool with Hyper-V isolation. All three run the same deterministic scenario code against research-owned synthetic fixtures. This compares complete deployment configurations and their configured controls; it does not isolate virtualization technology as the sole causal factor. Container Apps sessions are not Firecracker microVMs.

The original thesis proposes a 450-trial deterministic baseline. Azure revision 2 withdraws the 50 custom-session P3 cells because that service has no demonstrated selective egress and attributable denial evidence, leaving a 400-row proposed Azure baseline. This is a methodological amendment, not an equivalent reproduction, and requires review and approval before collection. The supplied matrix hash and order must be frozen only after implementation and pilot gates pass. A separate GPT-5 mini live-agent phase is specified in `10-GPT5-MINI-LIVE-AGENT-PHASE-DRAFT.md`; the prompt-injection design is in `14-PROMPT-INJECTION-ARM-DRAFT.md`. These remain separate from the deterministic baseline and are not frozen or measured. The scripted baseline does not require model inference.

The current VM candidate is Standard_F1as_v7 in East US: the subscription listing showed no SKU restriction and its reported regional and family quotas were each four available cores. Microsoft lists one vCPU and 4 GiB RAM for this size. Three profile-specific VMs would consume three cores, subject to actual regional capacity and other quota requirements. B2s was restricted in the regions checked. This replacement changes the proposed build guide's VM size and must be recorded in the final method; reported quota does not guarantee capacity. The final record must state the deployed size, image, region, versions, isolation settings and actual resource IDs.

Before measured collection, verify each platform's fixture reset, identity and permission boundary, session lifecycle and audit collection. Verify P3 selective egress using approved operations and controlled restricted destination tests, including direct IP and redirect probes, with independent enforcement evidence and explicit documentation of required platform exceptions. A failed connection, an unavailable platform, or missing logs is indeterminate, not proof of containment. Legitimate controls must succeed under the intended profile.

The controller, fixture administrator and verifier must be separate from the compromised workload and have only their required roles. Store per-trial evidence outside workload control, retain immutable or independently protected audit records as appropriate, and document retention and time synchronization. A local checksum detects accidental alteration but does not itself establish independent or tamper-proof evidence.

For each attempt, retain its planned run ID, configuration, timestamps, request outcome, relevant audit and fixture evidence, classification and failure reason. Distinguish unauthorized success, verified prevention, legitimate completion and indeterminate observations. Record interruptions and retries separately; do not silently overwrite an existing run or replace missing evidence. Final analysis must report denominators, indeterminate and missing observations, legitimate-control failures and limitations.
