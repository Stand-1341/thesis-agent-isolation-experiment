# Azure identity and fixture design — proposal, not validated

The current Docker resource service enforces a simulated profile in application code. It is useful for testing the harness but is not evidence of Azure RBAC or session isolation. Before the cloud trials, replace or supplement it with independently administered Azure resources and demonstrate the actual authorization boundary.

Use separate trusted controller, verifier and workload principals. Allocate the workload principal for exactly one deployment/profile combination; do not give the workload controller, verifier, session-executor, registry-write or evidence-write privileges. Create separate private synthetic Blob containers for authorized documents, restricted documents, authorized records, restricted records, active-session B state, and prior-execution state. Grant only the intended profile the required read or write data actions at the narrowest feasible container scope; use separate containers where distinct privileges are needed. Provision and independently verify role assignments and propagation before a measured trial. Blob RBAC applies to data access, and the role assignment scope must be validated against Microsoft's [Blob role guidance](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access).

`05-DOCKER-STARTER/infra/synthetic-fixtures-pilot.bicep` is a compiled candidate for these container-scoped roles. Its restricted profiles require a separately defined custom record role containing Blob read and write data actions but no delete action. Both templates compile but have not been deployed; real GET and update must succeed and DELETE must fail before treating the role as sufficient. The template does not prevent a principal from inheriting broader permissions elsewhere, and its accompanying identity-shape validator is not wired into deployment. Neither the template nor the validator proves separation. P1 and the trusted fixture controller retain the broader built-in Blob Data Contributor role for feasibility and fixture preparation.

For U6, create distinct session A and active session B fixtures and identities. Record that the request used A's identity, then test access to B's independently seeded marker. For U8, retain a synthetic prior-execution marker under a different identity and attempt access with a fresh execution identity. P1 must demonstrate that each operation can succeed when deliberately authorized; P2 and P3 must have independently evidenced denial while L1/L2 still succeed. U3 exposure and attempted dummy-token use remain separate outcomes. U4's mock API needs a separately verified authorization mechanism and audit; storage-container permissions alone do not implement it. U5/U7 require independent collector and network evidence. The exact mapping must be finalized and tested for every deployment arm, not inferred from this proposal.

Do not attach both P1 and P2/P3 user-assigned identities to one VM and assume an environment variable hides the stronger one. Microsoft describes the managed-identity security boundary as the Azure resource: code on the VM can request tokens for identities made available there. See [VM managed-identity token guidance](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-use-vm-token). The same exposure question must be tested for Function host identities and session-pool identities. Tokens already issued before a permission or identity change can remain usable; a profile change is not complete merely because configuration was updated.

The subscription's East US snapshot reports four total VM cores and one custom session pool. Standard_F1as_v7 is listed without a subscription restriction and its family has four unused cores; three one-core profile-specific VMs are a candidate, subject to actual capacity and other quotas. One pool cannot simultaneously represent three differently configured pools. Preserve the supplied interleaved order rather than grouping trials by profile. A single-pool approach needs demonstrably isolated profile changes, lifecycle handling, and sufficient time for role and token propagation. If the required isolation cannot be established within quota and budget, the design must be formally revised before collection rather than recording a setup failure as a prevention.

One candidate for the single-pool identity constraint is to have the trusted controller acquire a short-lived, profile-specific storage access token and send only that restricted token and the corresponding synthetic mock credential to a fresh, randomly identified session. The pool's registry-pull identity must remain unavailable to session code, and the controller's session-executor token must not reach it. The prototype checks the requested token's audience, principal and expiration claims as a guard against accidental mix-ups; it does not verify the JWT signature, and Azure Storage remains responsible for authentication and authorization. This design requires separate real workload principals and a pilot proving token non-disclosure, no cross-session or prior-execution credential retention, correct effective RBAC, and safe handling by proxies and logs. It does not solve the shared network policy: P1/P2 need collector access while P3 must be denied, so each profile transition needs independently validated network policy and session lifecycle handling. No design is accepted until those checks pass.

Record the exact identity ID, resource scope, role assignment, configuration version, effective access probe, and relevant independent audit reference for each run. Never store bearer tokens in results or logs. Final evidence must demonstrate the requested identity and resource state at the time of the trial; a configuration manifest alone cannot prove effective access.
