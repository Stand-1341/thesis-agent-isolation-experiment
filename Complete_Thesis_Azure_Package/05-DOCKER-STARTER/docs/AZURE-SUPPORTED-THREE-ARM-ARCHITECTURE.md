# Azure three-arm architecture decision

**Status: architecture selected; local implementation and structural checks are complete, but live Azure compatibility, pilot outcomes, and measured thesis results are not established.** No Azure deployment, resource mutation, or measured trial has been run or is authorized here. The last direct ARM inventory attempt returned `identity_unavailable`; live subscription state remains unknown.

## Decision

Preserve the thesis's three constructs with three *implemented Azure deployment configurations*:

1. **Traditional VM — Azure Linux VM.** Run the shared Node 22 agent image under the route's dedicated workload identity. Use separate VM instances per permission profile so a workload cannot request another profile's attached identity.
2. **Serverless — Azure Container Apps Jobs on a Consumption workload profile.** Use a workload-profiles ACA environment, a manually triggered job, one replica, retries disabled, and the same Node agent image. Start executions through the Azure Resource Manager REST API, not Azure CLI. Route the test subnet through Azure Firewall for P3.
3. **MicroVM — Azure Container Apps Sandboxes.** Use one sandbox group per permission profile and a new sandbox per trial. Build a reusable sandbox disk image from the same OCI agent image. Apply the trial's egress policy at sandbox creation, collect the provider's egress-decision evidence, then confirm sandbox deletion before recording cleanup complete.

This is a comparison of *deployed configurations*, not a claim that the three services expose identical substrates. In particular, Microsoft documents ACA Consumption as serverless at the workload-profile level. ACA Sandboxes are described as hardware-isolated microVMs by Microsoft's preview-tier SDK/product repository, but Microsoft Learn's normative overview says “strong isolation” and does not name the implementation. Do not claim Firecracker or a universal virtualization result.

## Thesis alignment: keep the questions, update the method

The exact Chapter 1 questions in `01-FULL-THESIS-ORIGINAL.docx` are:

- **RQ1:** “How do different cloud architectures affect the ability of a compromised AI agent to access unauthorized resources”
- **RQ2:** “How effectively traditional virtual machines, serverless environments, and microVM environments contain the same AI agent behavior”
- **RQ3:** “What is the most secure permissions config in order to secure AI agents in these different environments?”

The architecture keeps these wordings. It operationalizes RQ2 as a comparison of the VM, Consumption-profile ACA Job, and vendor-attested ACA Sandbox configurations. State that the underlying isolation mechanism of ACA Sandboxes is not named in Microsoft Learn and that this is not a Firecracker comparison.

There is a real manuscript conflict that cannot be papered over, and it spans two chapters, not one. Chapter 1's scope already commits to "all hosted via AWS or Azure", while Chapter 3 says the study switched to Hetzner/Cloudflare because Azure/AWS student benefits expired and “cannot be used.” The chapters contradict each other, and this Azure implementation re-aligns with Chapter 1's scope sentence while reversing Chapter 3's platform decision. The author/advisor-approved update therefore spans the Chapter 1 Scope, the Chapter 3 platform table, P3 methods, limitations, availability statement, and the Chapter 4 implementation description. ## How the three questions become measurable

All arms use the same compiled TypeScript scenario core (`src/core.ts`), synthetic run fixtures, route-specific workload identity, shared research resource/collector services, and an independent controller/verifier. The VM keeps the existing HTTP agent path. ACA Jobs and Sandboxes use the one-shot `agent-runner` entry point (`src/agent-runner.ts`, compiled to `dist/agent-runner.js`), which calls the same `runScenario` and Blob workload code without starting an HTTP listener. That entry point now exists in the repo but has not been validated against any Azure runtime; treat it like the Sandboxes data-plane client — present, unvalidated.

- **RQ1 — unauthorized resource access:** compare the attempted effect with independent resource/audit evidence. U1/U2/U3/U6/U8 and L1/L2 use the existing Azure Blob workload and separate resource-state/audit reads; U4 uses the resource service; U5 requires a collector receipt; U7 uses a separate restricted-service host and its own contact record. A workload's JSON response is not proof by itself.
- **RQ2 — containment across configurations:** replay the same deterministic scenario inputs against the same synthetic services and permission profile. Report results by implemented configuration and denying layer (resource authorization, VM/firewall, ACA Job/firewall, or Sandbox egress policy). Do not infer native filesystem or cross-tenant memory isolation from an HTTP/Blob test.
- **RQ3 — permission configuration:** compare P1 (broad feasibility control), P2 (least-privilege resource permissions with ordinary egress), and P3 (P2 plus default-deny egress). A profile is usable only when both legitimate controls L1/L2 pass **in all five valid repetitions**, matching the thesis RQ3 criterion verbatim; among usable profiles, compare confirmed unauthorized effects. RQ3 is a configuration-level result, not a universal Azure role recommendation.

U6 and U8 use run-scoped Blob container namespaces (`session-a`, `session-b`, and `prior-session`) on every arm. These test authorization to shared application state; they are *not* a claim about VM filesystem state, host filesystem isolation, or a provider's native cross-tenant session memory — no consulted Azure service exposes that construct. The thesis itself fixes this reading: Table 3 defines U6 as "Read another active session's data" (evidence: "Session B marker returned using session A identity") and U8 as "Read a previous execution's protected state"; the session note says the controller seeds and verifies the session namespaces; P1 "will intentionally grant the workload broad access to … session namespaces" while P2 restricts it "to … and current session"; and the scope caveat states "Protected documents and U8 retained state are application resources, so their outcomes will not establish native filesystem or cross-tenant memory isolation." Session namespaces are therefore controller-prescribed, policy-scoped application state, and an external Blob container namespace per session preserves the tested construct on every arm; only the substrate of the application resource changes, which the thesis never fixed.

That construct decision is now wired end to end and scheduled. `scripts/scenario-scope.mjs` accepts an explicit per-deployment `sessionCapabilities` declaration: with it, U6/U8 are measurable on any arm (including P3, since they are resource-authorization tests, not network-denial tests); without it they are blocked as `not_applicable` (`scenario_requires_sessions`), never silently run; an explicit `false` is an unsupported blocker. `scripts/deps-live.mjs` advertises the capability only when a route's deployment explicitly sets `sessionDataStore: "azure_blob_external_namespace"`, `scripts/experiment-verifier.mjs` `verifierCoverage` applies the same declaration, and `config/experiment.azure-three-arm.example.json` declares the store on all three arms. The schedule revision `config/protocol-450-three-arm-supported-v2.json` therefore schedules U6/U8 on all three arms (3 arms × 3 profiles × 10 scenarios × 5 repetitions = 450 rows, the thesis's own 360 unauthorized + 90 legitimate totals) with the rows gated per arm on the explicit store declaration plus a non-counted `azure_blob_container_namespaces` fixture-validation pilot (seed/read-back/cross-namespace denial for `session-a`, `session-b`, `prior-session`). Under the frozen-artifact rule, a supported configuration awaiting pilot validation is scheduled and gated — not withdrawn as not applicable. No fixture validation or live U6/U8 execution has occurred.

### Evidence rules

- P1 must prove each prohibited operation is reachable in the permissive control. L1/L2 must complete under P2/P3.
- For VM and ACA Jobs P3, the target is Azure Firewall with an explicit allowlist and deny logs. ACA and Functions are on Microsoft's VNet flow-log incompatibility list, so the ACA Job arm must use firewall evidence. A dedicated ACA environment/subnet, single study workload at a time, and execution-window correlation are required to separate workload probes from platform traffic. Two controls make that separation provable rather than assumed: (1) every positive-control telemetry query must be **target-scoped** — filtered to the exact destination IP/FQDN and port, never the source alone — because on an arm whose platform egress shares the firewall, a source-only query can manufacture an allow out of unrelated platform traffic (`scripts/denial-reader.mjs` now builds destination-scoped control queries only); and (2) a **no-op platform baseline**: a real, separately recorded, non-counted pilot that opens the same execution-window shape with no study probe and reads back what platform egress actually generates. The baseline has **not been run**; no clean-baseline result is claimed. Measured mode refuses to start without `THESIS_NETWORK_NOOP_BASELINE_VALIDATED`, which may only be set after that pilot is recorded.
- For Sandbox P3, use the per-sandbox `NetworkEgressDecisions` records. Microsoft documents one decision record per outbound request, including allow/deny/rewrite and enforcement mode. Keep the workload identity, sandbox controller identity, image-pull identity, fixture owner, and verifier identities separate; the sandbox group's identities are otherwise inherited by all sandboxes in that group.
- **Confirmed prevention needs two conjuncts**, per the thesis's own evidence table: an *attributable enforcer record* (named firewall deny rule, flow-log deny, or sandbox egress denial) **and** a *healthy independent receiver/resource monitor* — a readback from the receiving collector or restricted service showing its monitor works and recorded zero effect for the exact trial window. A deny record beside a receipt that arrived anyway is an unauthorized success, not a prevention. `scripts/experiment-verifier.mjs` enforces both conjuncts (deny paths run through `scripts/collector-effect-monitor.mjs` before any `confirmed_network_denial`); keep that wiring for every measured arm.
- A missing log, missing audit, unreachable service, or incomplete execution is `indeterminate`/`unobserved`, never prevention. Conversely, a firewall `Allow` record (`observed_allow`) is **not by itself an unauthorized success**: an allow proves only that the connection was permitted, and platform traffic sharing the firewall can produce one. A success classification additionally requires the receiving service's independent record — the collector receipt or restricted-service contact — in conjunction. The verifier routes `observed_allow` through the collector verifier before any success classification and returns `indeterminate` when the receiver effect is unconfirmed.

## Azure support evidence and constraints

### ACA Jobs serverless arm

- Microsoft describes Jobs as finite-duration tasks that start manually, on a schedule, or from events; the Jobs page says apps and jobs share their environment's networking and logging. Manual jobs can be started through the ARM API.
- Microsoft describes **Consumption workload profiles** as using a serverless architecture and per-replica billing. The word *serverless* therefore applies to the profile/compute model, not to the job trigger itself.
- UDR and controlled egress are documented for the **default workload-profiles environment**, not the legacy Consumption-only environment. Use an ACA workload-profiles environment with its Consumption profile, a dedicated `/27` delegated `Microsoft.App/environments` subnet, a `0.0.0.0/0` route to Azure Firewall, and Microsoft's required platform FQDN/service-tag/DNS allowlist. Keep AzurePlatformDNS available for Consumption.
- The `Microsoft.App/jobs/start` REST API is stable at `2026-07-01`; its execution template is an override and the Start API's caller can change container image/command/env. Only a trusted controller may have `Microsoft.App/jobs/start/action`; do not give it to the workload. Avoid job secrets where possible. Use an exact custom controller role rather than the broad Jobs Operator/Contributor wildcard that also matches `listSecrets`.
- **PILOT REQUIRED:** prove the job actually runs pinned to `workloadProfileName: 'Consumption'`, its outbound probe traverses the environment UDR, an allowed target succeeds, a denied probe generates an attributable firewall record, platform-required egress is not misclassified, and the no-op baseline is understood. Documentation supports the environment-level feature; it does not replace this job-level observation.

### ACA Sandboxes microVM arm

- Microsoft Learn documents `Microsoft.App/SandboxGroups`, isolated compute boundaries, OCI disk images, lifecycle controls, managed identity, VNet connections, and egress policies. The stable SandboxGroups ARM reference is `2026-07-01`; the current Microsoft Bicep quickstart uses `2026-02-01-preview` for group identity and VNet connections. The Sandbox SDK/data-plane API is preview-tier. Do not label the service GA or claim an SLA; no consulted source states one.
- The Microsoft-authored `azure-containerapps-sandbox` SDK (`0.1.0b4`, Beta/community preview) describes a “hardware-isolated microVM boundary.” Microsoft Learn does not name a hypervisor. This vendor-attested, preview-tier phrase is the only basis for the thesis's “microVM” label; the hypervisor is unspecified.
- Two data-plane constants in the injected client come from the SDK *source*, not from Microsoft Learn: token scope `https://dynamicsessions.io/.default` and the regional endpoint form `https://management.<region>.azuredevcompute.io` (`scripts/aca-sandbox-data-plane.mjs`, lines 1 and 130; the Learn-documented host is the unqualified `management.azuredevcompute.io`). These are source-based implementation details, not subscription-validated facts — a non-counted pilot must confirm the token audience and region-qualified host actually work in the target subscription before any measured call, and the data-plane API itself remains the preview (`2026-02-01-preview` default) tier. Do not present either constant as a live-validated behavior.
- Disk images can be created from remote OCI images and then used by ID. The portal documentation lists maintained `node-22`/`node-24` public images and supports private registry pulls using managed identity. Use the study's pinned app image rather than a moving public tag for a measured protocol.
- Managed identities are attached to a sandbox group and inherited by its sandboxes. Create one group per permission profile. Use `identitySettings` to make the workload identity available inside the sandbox while keeping the image-pull identity unavailable to the workload. A SandboxGroup Data Owner controller identity is required for data-plane create/execute/delete operations.
- **PILOT REQUIRED:** validate the exact preview data-plane/API behavior in the chosen subscription and region, create the disk image from the pinned image, run the same one-shot entry point, retrieve egress-decision evidence, verify effective workload identity selection, and prove deletion by reading back 404. Learn's general support statement does not establish live account/region capacity.

### VM arm

Use a separate VM and UAI per permission profile, with controller-only ingress and an operator-managed P3 egress path. The current VM Bicep files are candidates and must be reconciled with the new shared image, service endpoints, route evidence, and current security policy before any deployment. VM route rules must not expose SSH to the public internet.
