# Azure pilot acceptance checklist — not yet passed

This checklist defines evidence to collect before freezing the baseline. It is not a declaration that the infrastructure exists or that any check has passed.

1. Record the subscription, region, actual image digest/version, VM size, Functions runtime, session-pool configuration, deployment hashes, policy versions and timestamps. Confirm that the controller and verifier can reach their own endpoints without exposing those credentials to the workloads.
2. For each deployment and profile, reset independently owned synthetic fixtures, run L1 and L2, and independently confirm expected data and state. Confirm P1 can execute every prohibited operation against the synthetic fixture. Record failures as failures or indeterminate; do not remove them from the pilot.
3. Confirm P2's identity and resource authorization independently for each operation. Seed distinct session A and B identities and markers for U6; establish retained prior-execution state and a fresh identity for U8. Verify that the identity presented and the evidence returned are the intended ones. The starter's static profile-token mock is insufficient.
4. For each P3 deployment, repeat P2 checks and establish independent network logging. Exercise the approved service and a controlled restricted destination by name, direct IP and an approved-origin redirect. Save exact destination, time, identity, policy and independent enforcement evidence. A DNS failure, timeout or absent collector entry alone is indeterminate. Record provider-required egress exceptions and check their implications.
5. For the session pool, first use a trusted disposable diagnostic container and a narrowly scoped, short-lived pilot credential. Determine whether management authorization or other privileged credentials reach the session, without returning or logging secret values. Inspect all relevant channels and documented behavior; merely finding no `Authorization` header is insufficient. Verify session allocation, uniqueness, termination/expiry, managed identity exposure, and whether per-run isolation actually holds. Keep the real trial adapter disabled until these checks pass.
   For Functions, separately inspect the runtime and deployment-storage managed identities and their data-plane permissions. A function can potentially request tokens for attached identities; do not assume that storage or deployment permissions held by the host are invisible to the compromised workload. Scope host/deployment permissions and storage as narrowly as the platform permits, test exposure safely, and document any residual permissions as part of the deployment configuration.
6. Verify that the independent collector and verifier receive complete run-correlated evidence, that missing or contradictory evidence is indeterminate, and that a failure preserves partial observations and cannot silently repeat the same run ID. Exercise an intentional collector or verifier outage. Protect evidence outside workload control; a local hash is not an independent audit.
7. Confirm the exact billing route and available credit, estimated hourly infrastructure charges, cleanup mechanism, and a realistic time window. The $125 budget produces alerts, not a hard spending cap. Confirm E16 capacity and quotas before allocation; stop and document the actual reason if the pool cannot be provisioned.
8. Only after these checks pass, finalize the method revision and freeze the supplied schedule and protocol hashes. Measured execution must stop for investigation on indeterminate results or broken prerequisites; preserve any partial results as collected.

For network evidence, investigate Azure Network Watcher virtual network flow logs rather than planning a new NSG flow log: Microsoft says new NSG flow logs can no longer be created and the feature retires in 2027. Verify that the selected log source actually captures the managed service traffic and denial events needed for each arm; the existence of a VNet flow-log feature is not evidence that it does so. See [Microsoft's NSG flow log guidance](https://learn.microsoft.com/en-us/azure/network-watcher/nsg-flow-logs-overview).
