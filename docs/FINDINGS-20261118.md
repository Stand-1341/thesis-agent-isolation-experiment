# Findings — 400-row three-arm experiment, 2026-11-18

This is the consolidated findings record for the measured study. It covers the
dataset, the per-research-question findings, the infrastructure findings that had
to be fixed before any measurement was valid, and the threats to validity.

## 2. Findings by research question

### RQ1 — how architecture affects an agent's ability to reach unauthorized resources

The scenario set is U1–U8. Observed pattern (representative cells verified against
their sealed records):

- **P1 (broad feasibility control):** every unauthorized operation the workload was
  technically able to issue succeeded — protected document read (`U1`), restricted
  record write (`U2`), dummy credential read plus use (`U3`), prohibited API
  (`U4`), collector write (`U5`), cross-session read (`U6`), restricted service
  (`U7`), retained prior-session read (`U8`). This is the intended baseline: P1
  shows what a compromised agent can do when the identity is broadly scoped.
- **P2 (least privilege):** the resource-authorization scenarios are denied and
  independently attributed to the resource layer (`confirmed_resource_denial`, 85
  rows across the P2 and P3 routes; per-cell detail is in the sealed records). P2
  does not restrict egress, so calls to the collector and restricted service still
  reach the receiver.
- **P3 (P2 plus default-deny egress):** adds `confirmed_network_denial` on the two
  receiver-contact scenarios (`U5`, `U7`) from Azure Firewall deny records under
  the named rules `p3-deny-collector` / `p3-deny-restricted-service` (VM) and
  `functions-p3-deny-collector` / `functions-p3-deny-restricted-service`
  (Functions). Twenty such rows are in the dataset.
- **Legitimate controls:** `L1`/`L2` complete on every arm (80 `legitimate_completion`
  rows), so the denials are not a broken-service artefact.

Key RQ1 result: the same agent code produced materially different outcomes under
different permission configurations, and the denial layer differs by architecture —
resource authorization on P1/P2, plus attributable firewall denial on P3. The
sandbox arm shows resource-level outcomes but no sandbox network-denial claim,
because sandbox P3 is excluded.

### RQ2 — architecture comparison under identical agent behaviour

- All three configurations ran the same deterministic scenarios with the same
  synthetic fixtures and the same controller.
- The comparison is now complete for U1–U8 on the VM and Functions arms and for
  U1–U8 on the sandbox P1/P2 arms.
- Sandbox-specific operational finding: the platform egress proxy changes how the
  workload reaches private endpoints (see §3), so the sandbox arm is a *different
  substrate*, not a like-for-like network twin. That is stated as a scope
  limitation, not smoothed over.

### RQ3 — which permission configuration is most secure

- P1 is unusable as a secure configuration: it accounts for the majority of the
  174 unauthorized successes in the merged dataset.
- P2 removes resource-level unauthorized effect while leaving receiver contact
  possible.
- P3 removes the remaining receiver contact with attributable firewall denials.
- Session state is part of this argument, and only became measurable after the
  U6/U8 fix: P1 reads another session's namespace and a prior execution's retained
  namespace; P2/P3 are denied. That is direct evidence that session scoping, not
  just document scoping, is doing work in the least-privilege profile.

## 3. Infrastructure findings (why the first dataset was incomplete)

These were defects, not study results. Each was fixed and re-verified.

1. **Sandbox had no network path.** No customer VNet connection, no NSG allowance
   for the sandbox subnet, and an image without `ca-certificates`. Fixed with the
   `sandbox-egress` subnet (`10.48.11.0/24`), VNet connection on all three sandbox
   groups, NSG rules, and a rebuilt digest-pinned image.
2. **Platform egress proxy intercepts TCP/443** and rejects IP-based SNI. The
   research receiver is therefore also exposed to the sandbox arm on
   `10.48.9.4:10443` (same nginx block, same certificate, same application).
3. **Customer-VNet warm-up.** A new sandbox needs ~20 seconds before private
   addresses accept connections. Added a bounded TCP readiness probe before each
   sandbox execution.
4. **Functions access restrictions** allowed only the research host's old public
   address; every Functions trial stopped at the first fixture reset with HTTP 403.
   Added the current egress address.
5. **VM agent had no `RESTRICTED_URL`**, so U7 failed before any network call.
   Added it on P1/P2/P3.
6. **VM verifier key alias mismatch** (`THESIS_AZURE_VM_*` vs `THESIS_VM_*`) turned
   clean HTTP responses into "evidence read failed". Both names now exported.
7. **P3 deny attribution only knew the collector destination**, so U7 could not be
   attributed even when the firewall denied it. The denial reader now resolves a
   per-scenario destination and named deny rule.

## 4. Method finding: `not_applicable` was a bug

The 80 U6/U8 cells were reported `not_applicable('scenario_requires_sessions')`
although the protocol declared the external namespace store, the fixture adapters
seeded `session-a`/`session-b`/`prior-session`, and scope analysis called the rows
measurable. The Blob verifier simply never received `sessionDataCapabilities`.

After passing the declaration, U6 = 19 success / 19 denial / 2 indeterminate and
U8 = 20 success / 20 denial. This is the expected permission signal, not an
artefact. See `docs/RESEARCH-QUESTION-COVERAGE-20261118.md`.

## 6. Threats to validity

- **Substrate, not equivalence.** These are three implemented configurations, not
  identical substrates. Sandbox behaviour is additionally shaped by its egress
  proxy and the alternate research port.
- **Sandbox TLS.** Generic fetches inside the ephemeral sandbox run with TLS
  verification disabled because the proxy CA is not reliably materialised there;
  research/collector/restricted calls still pin the private CA.
- **U6/U8 construct.** Application-level shared-state authorization on run-scoped
  Blob namespaces; not host filesystem or cross-tenant memory isolation.
- **Per-arm fixtures.** Fixture seeding uses the controller identity; the workload
  identity is separate. Cross-namespace denial is measured under the workload
  identity.
- **Repair mixing.** 13 cells come from `v10`/`v11`/`v13` and 80 from `v12`; every
  replacement is listed in the evidence summary and changes no other cell.
- **Two U6 retries** were still indeterminate when this document was written.
